1. Introduction

This document provides a comprehensive reference for the Document Generation API. It covers authentication, endpoint descriptions, request/response formats, error handling, and best practices for integration.

The API follows RESTful conventions and uses JSON for all request and response bodies. Authentication is handled via OAuth 2.0 bearer tokens. All timestamps are in ISO 8601 format and all monetary values are in the smallest currency unit (e.g., cents for USD).

Rate limits are enforced per API key. The default rate limit is 100 requests per minute for standard plans and 1,000 requests per minute for enterprise plans. Rate limit headers are included in all responses.

2. Authentication

All API requests must include a valid authentication token. The API supports two authentication methods: API keys for server-to-server communication and OAuth 2.0 for user-delegated access.

2.1 API Key Authentication

API keys are long-lived credentials suitable for server-to-server integration. Each key is associated with a specific organization and inherits the organization's permissions. API keys should be passed in the Authorization header using the Bearer scheme.

Keys can be rotated at any time through the dashboard without affecting active sessions. We recommend rotating keys at least every 90 days as a security best practice.

2.2 OAuth 2.0 Flow

For applications that act on behalf of users, the OAuth 2.0 authorization code flow is required. The flow begins with redirecting the user to the authorization endpoint, where they grant permissions to your application.

After authorization, your application exchanges the authorization code for an access token and a refresh token. Access tokens expire after one hour; use the refresh token to obtain new access tokens without requiring user interaction.

2.3 Token Refresh

Refresh tokens are valid for 30 days from their last use. If a refresh token expires, the user must re-authorize your application. To prevent this, ensure your application refreshes tokens proactively before expiration.

3. API Endpoints

The API exposes endpoints organized by resource type. All endpoints use the base URL https://api.example.com/v2 and require authentication.

3.1 Document Creation

Creates a new document from a template and data payload. The template must be previously registered through the template management endpoints. The data payload is validated against the template's schema before processing begins.

Document creation is asynchronous for payloads larger than 1MB. For smaller payloads, the response includes the generated document directly. For larger payloads, a job ID is returned that can be polled for completion status.

3.2 Document Retrieval

Retrieves a previously generated document by its unique identifier. The response format depends on the Accept header: application/pdf returns the binary PDF, while application/json returns document metadata and a download URL.

Documents are retained for 90 days after generation. After this period, the document is automatically deleted and the endpoint returns a 404 response. Enterprise plans can configure custom retention periods up to 7 years.

3.3 Batch Processing

The batch endpoint accepts an array of document creation requests and processes them concurrently. Each item in the batch is independent: failures in individual items do not affect the processing of other items.

Batch requests are limited to 500 items per request. For larger volumes, submit multiple batch requests. The batch endpoint returns a batch ID that can be used to monitor progress and retrieve results.

3.4 Template Management

Templates define the layout and structure of generated documents. Each template consists of an HTML body with Tailwind CSS styling and optional template expressions for dynamic content. Templates are versioned: updates create new versions while preserving the ability to generate documents from previous versions.

Template validation occurs at upload time. The system checks for valid HTML structure, resolves all CSS classes, and verifies that template expressions reference valid schema fields. Invalid templates are rejected with detailed error messages.

4. Error Handling

The API uses standard HTTP status codes to indicate success or failure. All error responses include a JSON body with a machine-readable error code, a human-readable message, and an optional details field with additional context.

Client errors (4xx) indicate problems with the request that can be fixed by the caller. Server errors (5xx) indicate temporary issues that should be retried with exponential backoff. The Retry-After header, when present, indicates the recommended wait time before retrying.

Validation errors (422) include a field-level breakdown in the details array. Each entry specifies the field path, the validation rule that failed, and the expected format. This enables client-side form validation without additional API calls.

5. Rate Limiting

Rate limits protect the API from abuse and ensure fair usage across all clients. Limits are enforced per API key using a sliding window algorithm. When the limit is exceeded, the API returns a 429 Too Many Requests response.

5.1 Rate Limit Headers

Every API response includes rate limit headers: X-RateLimit-Limit (maximum requests per window), X-RateLimit-Remaining (requests remaining in the current window), and X-RateLimit-Reset (Unix timestamp when the window resets).

Applications should monitor these headers and implement proactive throttling to avoid hitting limits. Libraries for most popular programming languages are available in our SDK repository.

5.2 Burst Handling

Short bursts above the rate limit are tolerated up to 150% of the limit for a maximum of 10 seconds. This accommodates legitimate traffic spikes during batch operations or page loads. Sustained traffic above the limit is rejected immediately.

6. Webhooks

Webhooks provide real-time notifications for asynchronous events such as document generation completion, batch processing progress, and template validation results. Webhook endpoints must use HTTPS and respond with a 2xx status code within 30 seconds.

Each webhook delivery includes a signature in the X-Webhook-Signature header, computed using HMAC-SHA256 with your webhook secret. Always verify this signature before processing the payload to prevent spoofing attacks.

Failed deliveries are retried up to 5 times with exponential backoff (1min, 5min, 30min, 2hr, 24hr). After all retries are exhausted, the webhook is marked as failed and an email notification is sent to the organization's admin contacts.

7. SDKs and Libraries

Official SDKs are available for Python, Node.js, Java, Go, and Ruby. Each SDK wraps the REST API with idiomatic language constructs, handles authentication, implements automatic retry logic, and provides type-safe request and response objects.

Community-maintained SDKs exist for PHP, C#, Rust, and Swift. While not officially supported, these libraries follow our SDK design guidelines and are regularly tested against the latest API version.

All SDKs are open-source and available on GitHub. Contributions are welcome following our contribution guidelines. Breaking changes are communicated at least 6 months in advance through our developer newsletter and API changelog.
